# Paper 2: experiment plan and related work

Central question: **As AI tools become part of development, what explains how quickly pull requests move through review and merge?**

This study concerns merge duration conditional on eventual merging. The current snapshot has total duration and aggregate review counts, not review-stage timestamps. It cannot locate delays within individual review stages or identify which code was generated by AI. Copilot seat status records access, not use or authorship.

## Questions and experiments

| Question | Comparison | Evidence to report |
| --- | --- | --- |
| RQ1: What information do PR change characteristics, descriptions, and completed review activity provide about merge duration? | Tabular-only versus TF-IDF/SVD versus frozen embeddings; matched feature ablations | Validation macro F1, class recall, ordered errors, and duration errors; text representation fitted on training PRs only |
| RQ2: How does prediction transfer across repositories and merge periods? | Unseen repositories versus later merge periods within known repositories | Performance, per-repository variation, class distributions, and training/validation gaps; keep temporal interpretation retrospective |
| RQ3: Does Copilot access add predictive information, and do error patterns differ between access groups? | `description` versus `copilot`; `review` versus `review_copilot`; subgroup diagnostics | Matched feature comparisons and support counts; descriptive associations, no causal tool-effect claim |

The completed complexity score paper contributes a measurement framework. This paper investigates prediction and generalization; it does not redefine that score. The score is excluded from model inputs because it includes review information and would obscure review ablations.

## Development protocol

1. Preserve the original run directory. Its test results have already informed model development.
2. Reuse its `splits.csv.gz` and prespecified duration boundaries when testing richer representations on the same population. The supplied dataset path remains `data/cleaned_public.csv`.
3. Start with tabular and TF-IDF multiclass experiments, training diagnostics, and the `description`/`review` feature sets. Compare validation results before increasing the experiment matrix.
4. Compare ordinal prediction and log-duration regression on the same PR partitions and class boundaries. Do not change class counts merely to obtain a larger accuracy percentage.
5. Add frozen embeddings and Copilot ablations as prespecified comparisons. Report every attempted variant. Do not select a final configuration using test scores.
6. Run the known-repository merge-period protocol separately. It answers a different deployment question and can include a different subset of PRs. Report that difference, use the same practical class cutoffs, and avoid calling an easier split an improvement on unseen-repository generalization.
7. For a final confirmatory evaluation, collect independently held-out PRs with verified feature snapshots and timestamps. A new seed on the original data does not create a genuinely untouched final test. The saved-model evaluator checks PR key overlap and performs no fitting; independence and prior exposure still require researcher verification.

The enhanced runner defaults to training/validation evaluation. `--evaluate-test` produces explicitly exploratory internal test results. `--external-test` accepts a separate prepared file and rejects PR key overlap with all development data. Never treat nonoverlap alone as proof of independent collection or opening-time feature availability.

## Model choices and interpretation

- **Multiclass XGBoost:** ordinary three-class probability prediction; choose the configuration by validation macro F1.
- **Ordinal XGBoost:** two cumulative binary models estimate P(class > fast) and P(class > medium). Pool crossing probabilities to their mean, giving a monotonic distribution. Predict the posterior median class, which targets absolute class error. Choose by validation mean absolute class error. This is a separate decision rule and may trade exact accuracy for smaller mistakes.
- **Duration regression:** XGBoost predicts log(1 + minutes). Choose by validation log MAE. Report MAE and median absolute error in actual minutes as well as log MAE/RMSE. Clip negative predictions to zero and bound logs at 30 before exponentiation for numerical stability. These predictions estimate duration conditional on merging, not acceptance probability.
- **Baselines:** training majority class, training median class, training median duration, logistic regression, and ridge regression. Baselines and XGBoost receive matching rows and fitted representations.
- **Diagnostics:** validation confusion matrices, per-repository and Copilot-group error summaries, extreme-class error rate, quadratic weighted kappa, training sample scores, and boosting learning curves. A train/validation gap can reflect distribution shift as well as overfitting; it is not a standalone diagnosis.
- **Early stopping:** final validation loss controls stopping. Train diagnostics are logged as a separate first evaluation set and never control stopping. The selected configuration uses the task-specific validation metric listed above.
- **Timing limits:** tabular inputs, titles, and bodies may reflect final state. Review counts are completed-process observations. Opening-time deployment requires additional data. No creation timestamp is reconstructed from a rounded merge day.

## Related work to read and compare

| Work | What it contributes | Connection and limits |
| --- | --- | --- |
| Lima Júnior, Soares, and Plastino (2021), [Predicting the lifetime of pull requests in open-source projects](https://doi.org/10.1002/smr.2337) | Regression and classification into five time intervals; 20 evaluated projects; abstract reports 45.28% average accuracy | Compare predictors, class definitions, baselines, and evaluation protocols. Do not compare its percentage directly with ours: lifetime/outcome definitions, populations, and splits can differ. |
| Banyongrakkul and Phoomvuthisarn (2024), [DeepPull: Deep Learning-Based Approach for Predicting Reopening, Decision, and Lifetime of Pull Requests on GitHub Open-Source Projects](https://doi.org/10.1007/978-3-031-61753-9_6) | Combines textual and tabular sources for multiple PR outcomes | Motivates actual text representations. Our TF-IDF/embedding plus XGBoost approach is inspired by multimodal inputs; it is not a reproduction of DeepPull's architecture or reported performance. [Author-released dataset](https://zenodo.org/records/10054035) may support external comparison after schema, target, overlap, and licensing checks. |
| Maddila, Bansal, and Nagappan (2019), [Predicting Pull Request Completion Time: A Case Study on Large Scale Cloud Services](https://doi.org/10.1145/3338906.3340457) | Industrial completion-time prediction and developer-facing deployment | Supports the practical motivation and evaluation of duration estimates. Borrow feature and validation ideas only when they can be computed with the available information. |
| Maddila and colleagues, [Nudge: Accelerating Overdue Pull Requests toward Completion](https://doi.org/10.1145/3544791), TOSEM (online 2022; volume 32, issue 2) | Combines lifetime prediction, activity detection, and identifying whom to notify | Motivates future actionable delay detection. We do not implement reminders, identify blockers, or claim intervention benefits from offline prediction. |
| Kudrjavets, Nagappan, and Rastogi (2022), [Do Small Code Changes Merge Faster? A Multi-Language Empirical Investigation](https://arxiv.org/abs/2203.05045) | Finds a weak relationship between size and merge duration | Motivates richer content and workflow information. Its observational findings do not prove a predictive ceiling for our dataset. |
| Ehsani and colleagues (2026 preprint), [Where Do AI Coding Agents Fail? An Empirical Study of Failed Agentic Pull Requests in GitHub](https://arxiv.org/abs/2601.15195) | Examines task types, code changes, CI, and review dynamics for agent-authored PRs | Provides AI workflow context and possible enrichment features. Their agent-authorship labels differ from Copilot seat access. Our merged-only data cannot reproduce merged-versus-rejected analyses. |

These references motivate the design; they do not guarantee accuracy or establish novelty by themselves. Read the full methods before claiming a replication or direct improvement. A contribution needs substantive findings about information sources and generalization, a transparent timing audit, and an independently evaluated artifact.

## Additional collection that would strengthen the study

- Exact opening and completion timestamps, plus verified opening snapshots of titles, descriptions, and diffs.
- Author history and repository workload computed strictly before the prediction time.
- CI/check events and review timestamps, captured up to a clearly specified prediction landmark.
- Precise exposure definitions for AI tool use, if a question about use rather than access is intended.
- Nonmerged/open PRs with observation windows if expanding from conditional merge duration to acceptance or censored time-to-event models.

These fields are not fabricated from the 37-column snapshot. Survival modeling is future work unless nonmerged/censored observations and reliable event timing are collected.
